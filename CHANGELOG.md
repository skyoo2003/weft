# Changelog

What a caller has to change. Not what changed — `git log -p` already says that, and each tag's release notes are generated from the pull requests that went into it.

Three things can force work on your side, and each is decided by a file rather than by this document:

| What | Where it is decided | How you find out |
| --- | --- | --- |
| The exported API of any package under `pkg/` | `pkg/engine/testdata/engine_api.txt` for `engine`, `public_api.txt` for every other package there | those files' diff between the two tags. Usually your build stops compiling as well, but not always — an exported constant that changes value re-ranks your results and compiles cleanly, so the diff is the signal and the compiler is only a bonus |
| The on-disk format | `formatVersion` in `pkg/engine/segment.go` | `Open` returns `ErrBadVersion` |
| The minimum Go version | the `go` line in `go.mod` | `GOTOOLCHAIN=auto`, the default, downloads that version and builds; `GOTOOLCHAIN=local` refuses |

Those three have kinds of their own below. A release that moved none of them and has nothing else worth announcing gets no entry at all: absence is the claim.

**The module version and the format version are independent.** `v0.2.0` does not imply format 2, and a format bump does not force a major version, because weft is v0.x and its API can break inside a minor either way. They count two different things: one an API you compile against, one bytes already on your disk.

Entries are written with [changie](https://changie.dev) as the change is made, not reconstructed at release time. `make changelog-new` adds one.

## Unreleased

### Exported API

- Baseline. The surface at this tag is whatever pkg/engine/testdata/engine_api.txt and public_api.txt record at the tagged commit; every later release states its diff against them rather than restating the whole surface. ([#9](https://github.com/skyoo2003/weft/issues/9))
- Three additions, no changes: Scrub(dir) verifies every byte of a committed index, which Open no longer does; Index.Close releases the mappings an opened index holds; Index.Merge collapses the oldest segments once the count passes eight. The six read methods a scorer calls are untouched, which is the milestone 3 claim. ([#9](https://github.com/skyoo2003/weft/issues/9))
- engine.Index.Nearest(v []float32, k int) []DocID returns the DocIDs worth scoring exactly for a query vector, at least k of them when the index holds that many vectors. It computes no score: the engine knows which documents are geometrically plausible, and the metric stays with the caller (docs/DECISIONS.md D-008). The result is ascending, free of repeats, and wider than the answer — a segment with no partition offers every id it holds, documents carrying no vector included, so a caller still skips what it cannot score. The one thing left out is a segment holding no vectors at all: every candidate it could offer is one the caller would skip, so offering them would only buy a decode of the segment. It is not a promise that the exact top k are among them; docs/EVAL.md section 5.14 publishes the measured recall against a brute-force scan. ([#11](https://github.com/skyoo2003/weft/issues/11))
- One addition, no changes: `engine.Index.Vector(DocID) ([]float32, bool)` returns a document's vector without decoding the rest of it. `Doc` cannot know which fields its caller will read, so it materialises all of them — key, text, links — and a scorer that scans candidates for their vectors was paying for a copy of each document's text at every candidate it looked at. Measured on a synthetic corpus: scoring 64 documents allocated 4,208,024 bytes against 13,312 for the same vectors with 4 MiB less text. Everything `Doc` guarantees holds — a committed record is still checked against its own seeded checksum, so damage and a wrong id answer false rather than returning a plausible vector, and the returned slice must not be modified for the same reason `Document` gives. A document carrying no vector answers false, which is also the answer for an id that was never assigned. The six read methods a scorer already called are untouched, `pkg/fusion` is unchanged, and `go list -m all` is still one line. The reasoning, including the two routes not taken, is `docs/DECISIONS.md` D-015. ([#14](https://github.com/skyoo2003/weft/issues/14))

### On-disk format

- Version 1, described in docs/FORMAT.md. Nothing to migrate from — this is the first tag. ([#9](https://github.com/skyoo2003/weft/issues/9))
- Version 2. Version 1 indexes are refused with ErrBadVersion and are not migrated — weft has no users and the only v1 directory in existence is rebuildable, which is an argument available exactly once (docs/DECISIONS.md D-007). New sections docoff and keys let a DocID or a Key reach its document without decoding the documents in front of it; per-unit checksums let one record, block or entry be verified without reading the whole file; the manifest's segment entries now carry (name, base, count). ([#9](https://github.com/skyoo2003/weft/issues/9))
- Version 3. One new section, ivf, holding an IVF-flat partition of a segment's vectors: spherical k-means centroids and the segment-local DocIDs assigned to each, each inverted list sealed with a CRC-32C seeded with its own list number. Version 2 indexes are read without conversion — a v2 segment reports no partition and answers with every id it holds, which is the same fallback a pending segment and a segment below 16,384 documents already need, so it costs a branch that had to exist anyway. Index.Merge upgrades a v2 generation to v3 as a side effect of the maintenance an index already performs. Version 1 is still refused. This discharges the obligation FORMAT.md section 7.6 placed on a version 3 (docs/DECISIONS.md D-008). ([#11](https://github.com/skyoo2003/weft/issues/11))

### Minimum Go

- 1.26. This is the floor, not a tested ceiling — newer is untested rather than unsupported, and the gate pins this one line rather than a matrix. ([#9](https://github.com/skyoo2003/weft/issues/9))

### Added

- `weft-eval recall` and `make recall` measure what nDCG cannot see about an approximate vector index: overlap with a brute-force scan, candidates scored per query, latency both ways, and the working set a query actually reaches in bytes and in distinct pages. A partition that loses half the true neighbours holds nDCG steady when the neighbours it lost were unjudged, which on 50 queries against 171,332 documents is most of them. ([#11](https://github.com/skyoo2003/weft/issues/11))
- `weft-eval bench` and `make bench` publish a latency distribution rather than a mean: an open-loop arrival ladder at 12.5%, 25%, 50%, 100% and 200% of measured sequential throughput, with each request timed from its intended send time so a stall lands on every request it delayed. Every rung reports p50/p95/p99/p99.9 as measured and with the stop-the-world time charged to each sample removed, alongside GC cycles, GC CPU share, page faults and context switches. A quantile without 100 samples beyond it is left out rather than printed, and which rung the headline is quoted at is fixed by a rule registered before the numbers existed. docs/PERF.md is the measurement design. ([#12](https://github.com/skyoo2003/weft/issues/12))
- docs/PERF.md publishes the first latency distribution this project has had. weft's p99 on the 171,332-document evaluation corpus is 98.041ms at the registered load point, of which stop-the-world accounts for 279us — 0.28%. bleve v2.6.0 on the same machine, corpus, query set, arm and load generator is 47.123ms, so weft is 2.08x it against the order-of-magnitude bar the PRD set. The comparison lives in bench/, a separate module, so `go list -m all` still prints one line. Two predictions were wrong: the tail is neither the collector nor the 210MiB working set, and what it actually is turns out to be a property of open-loop measurement that bleve shares. ([#12](https://github.com/skyoo2003/weft/issues/12))
- `weft-eval bench -writes` prices what a commit costs the reads running against it, which is the question docs/FINDINGS.md milestone 3b left open. It copies the index first — a commit against the published evaluation corpus would rewrite the thing every measured number names — then drops one commit into a read load and splits the latencies by whether a request was due while the write lock was held. On the evaluation corpus a commit adding 20,000 documents holds the lock 11.641s and the worst read caught in it waits 13.142s. A commit below the partition floor skips the training entirely and costs 36ms, so the cost scales with the size of the commit rather than the size of the index. ([#12](https://github.com/skyoo2003/weft/issues/12))
- `weft-eval bench -rates 3.21,6.42,12.84,25.67` runs the rates you name, in order, instead of the sweep `-rate 0` derives from that run's sequential throughput. It exists because a derived sweep cannot ask whether a rung's result depends on the rungs before it: two runs land on different rates, so the history is confounded with the load. A named ladder gets no saturation point and no headline — it satisfies every shape check the load-point rule makes, and an operator who chose the rungs has chosen the load point at one remove, so provenance now travels with the rates rather than being inferred from their shape. Every entry is held to the bounds a lone `-rate` gets, at flag time rather than at dispatch, because a four-rung sweep whose third entry was a typo is ninety minutes spent before anything says so. The experiment it was built for is registered in `docs/PERF.md` section 5.2. No exported API under `pkg/` moved. ([#14](https://github.com/skyoo2003/weft/issues/14))

### Changed

- Open maps segments instead of decoding them, so opening an index costs the vocabulary rather than the corpus — 54 ms against 979 ms on a 171,332-document index. Commit writes only what was added since the last one; on a 7.2 MB corpus a commit after one Add writes 245 bytes, and previous generations are left untouched. Whole-file verification moved from Open into Scrub: damage inside a unit is still refused when that unit is read, and damage in bytes no decoder reaches now needs Scrub to find. ([#9](https://github.com/skyoo2003/weft/issues/9))
- scorer/vector no longer scans the whole corpus. Its loop now reads engine.Index.Nearest, which on the evaluation corpus scores 30,549 documents of 171,332 per query and returns a query 4.6 times faster. The consequence a caller has to know about is that vector results are now approximate: recall@10 against an exact scan is 0.992 and nDCG@10 for the text+vector arm moved 0.6233 to 0.6211. Nothing about the scorer's contract changed — zero norms, non-finite queries, ErrDimMismatch and context polling all behave exactly as before, and all twelve of its existing tests pass unmodified. A segment with no partition is still scored exactly. ([#11](https://github.com/skyoo2003/weft/issues/11))
- `cmd/weft` fuses the graph stream at a tenth of a vote instead of a full one, so the demo now agrees with the advice the rest of the project gives about that scorer: milestone 4 measured it contributing +0.0000 at its best weight and −0.1227 at equal weight, and both the README limitations table and the scorer's own package documentation say to weight it down. Rankings printed by the demo change. No exported API under `pkg/` moved — both golden files are byte-identical, and the weights index by stream position, so fusion still does not learn what a graph scorer is. ([#13](https://github.com/skyoo2003/weft/issues/13))
- `weft-eval bench` and the bleve comparison refuse to publish figures they did not measure. A rung reports how much wall time the process did not run for — the monotonic clock does not advance while a machine sleeps, so a ladder measured across thirteen hours of clamshell sleep previously reported every rung finishing exactly on schedule, with no shed and a headline 0.8% from the published one. Past a five-second tolerance the rung prints SUSPENDED and the summary refuses the run. A ladder cut short no longer prints a saturation point or a headline either: both commands now pass the ladder they intended rather than the rungs they reached, so an interrupted sweep is no longer indistinguishable from a complete shorter one. Rungs also print progress every thirty seconds, from a goroutine that serves no request. No exported API under `pkg/` moved — `git diff --stat pkg/` is empty for the whole milestone. ([#14](https://github.com/skyoo2003/weft/issues/14))
- Every rung of `weft-eval bench` now says how much *it* raised the process's peak resident set, or that it raised nothing and the figure beside it therefore belongs to an earlier rung. `ru_maxrss` is a high-water mark the kernel never lowers and offers no way to reset, so a rung on a ladder has always printed the peak the whole process had reached by the end of it — labelled `(process)`, and read anyway as that rung's. A pass line of the form "RSS under N at this rate" was judged against 345.2 MiB that had been reached two rungs earlier at half the rate before anything said so. The increase is the one per-rung memory statement the syscall supports; what it still cannot give is a rung's own peak once an earlier rung has set a higher mark, and `docs/PERF.md` section 2.7 says so rather than leaving it to be assumed. No published figure moves. No exported API under `pkg/` moved. ([#14](https://github.com/skyoo2003/weft/issues/14))

### Fixed

- Five defects in the milestone 5 load instrument, all found by review and all biased toward a flattering number. GCPause was charged over a shorter window than the latency it is subtracted from, so 64% of the p99 elapsed before accounting began; -writes stamped its commit window after the Add loop, filing the writer's own lock contention under the baseline it is compared against; the unloaded median was 50 samples where the package's own rule wants 200, and it is the denominator of every arrival rate; GCPauseTotal allocated per call, producing ~150 MiB of garbage per ladder that the report charged to the query; and GC CPU share was a ratio of process-since-start totals rather than of per-rung differences. Every published figure was re-measured afterwards — the headline p99 moved 98.041ms to 108.193ms and the collector's share of it 0.28% to 0.38%. ([#12](https://github.com/skyoo2003/weft/issues/12))

### Security

- Commit now creates its index directory and segment directories with mode 0o700 rather than 0o755. The corpus is the caller's data and nothing weft does needs another user on the machine to read it — including the caller's own group, which 0o750 would let read the 0o644 segment files inside. ([#9](https://github.com/skyoo2003/weft/issues/9))

### Documentation

- A published latency figure has been measured twice and come back. `docs/PERF.md` had required "the median of three repetitions with the spread beside it" since the first performance milestone and had never produced one: the same arrival rate gave 37.9 ms once and 1.539 s twice, and the rule directing the median turned out to be comparing two different things. What a repetition has to hold constant is the ladder in front of it, and its depth — reached as the fourth rung of a ladder whose earlier rungs each ran ten thousand samples, the rate that could not be repeated came back within 0.07% of its first observation, shed 0 both times, with the collector's cycle count within 0.12%. A prefix of the same shape at a fifth of the depth is worse than no prefix at all, and lowering the concurrency cap moves the shape of the collapse without moving the knee. The repaired procedure is `docs/PERF.md` section 3 rule 3, the reasoning and what would refute it are `docs/DECISIONS.md` D-013, and every figure and caveat is `docs/FINDINGS.md` milestone 8. No figure already published has been re-measured under the repaired rule; each remains a single observation and is labelled as one. No exported API under `pkg/` moved. ([#14](https://github.com/skyoo2003/weft/issues/14))
