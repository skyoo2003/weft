# Changelog

What a caller has to change. Not what changed — `git log -p` already says that, and each tag's release notes are generated from the pull requests that went into it.

Three things can force work on your side, and each is decided by a file rather than by this document:

| What | Where it is decided | How you find out |
| --- | --- | --- |
| The exported API of any package under `pkg/` | `pkg/engine/testdata/engine_api.txt` for `engine`, `public_api.txt` for every other package there | those files' diff between the two tags. Usually your build stops compiling as well, but not always — an exported constant that changes value re-ranks your results and compiles cleanly, so the diff is the signal and the compiler is only a bonus |
| The on-disk format | `formatVersion` in `pkg/engine/segment.go` | `Open` returns `ErrBadVersion` |
| The minimum Go version | the `go` line in `go.mod` | `GOTOOLCHAIN=auto`, the default, downloads that version and builds; `GOTOOLCHAIN=local` refuses |

Those three have kinds of their own below. A release that moved none of them and has nothing else worth announcing gets no entry at all: absence is the claim.

**The module version and the format version are independent.** `v0.2.0` does not imply format 2, and a format bump does not force a major version, because weft is v0.x and its API can break inside a minor either way. They count two different things: one an API you compile against, one bytes already on your disk.

Entries are written with [changie](https://changie.dev) as the change is made, not reconstructed at release time. `make changelog-new` adds one.

## Unreleased

### Exported API

- Baseline. The surface at this tag is whatever pkg/engine/testdata/engine_api.txt and public_api.txt record at the tagged commit; every later release states its diff against them rather than restating the whole surface. ([#9](https://github.com/skyoo2003/weft/issues/9))
- Three additions, no changes: Scrub(dir) verifies every byte of a committed index, which Open no longer does; Index.Close releases the mappings an opened index holds; Index.Merge collapses the oldest segments once the count passes eight. The six read methods a scorer calls are untouched, which is the milestone 3 claim. ([#9](https://github.com/skyoo2003/weft/issues/9))
- engine.Index.Nearest(v []float32, k int) []DocID returns the DocIDs worth scoring exactly for a query vector, at least k of them when the index holds that many vectors. It computes no score: the engine knows which documents are geometrically plausible, and the metric stays with the caller (docs/DECISIONS.md D-008). The result is ascending, free of repeats, and wider than the answer — a segment with no partition offers every id it holds, documents carrying no vector included, so a caller still skips what it cannot score. The one thing left out is a segment holding no vectors at all: every candidate it could offer is one the caller would skip, so offering them would only buy a decode of the segment. It is not a promise that the exact top k are among them; docs/EVAL.md section 5.14 publishes the measured recall against a brute-force scan. ([#11](https://github.com/skyoo2003/weft/issues/11))
- One addition, no changes: `engine.Index.Vector(DocID) ([]float32, bool)` returns a document's vector without decoding the rest of it. `Doc` cannot know which fields its caller will read, so it materialises all of them — key, text, links — and a scorer that scans candidates for their vectors was paying for a copy of each document's text at every candidate it looked at. Measured on a synthetic corpus: scoring 64 documents allocated 4,208,024 bytes against 13,312 for the same vectors with 4 MiB less text. Everything `Doc` guarantees holds — a committed record is still checked against its own seeded checksum, so damage and a wrong id answer false rather than returning a plausible vector, and the returned slice must not be modified for the same reason `Document` gives. A document carrying no vector answers false, which is also the answer for an id that was never assigned. The six read methods a scorer already called are untouched, `pkg/fusion` is unchanged, and `go list -m all` is still one line. The reasoning, including the two routes not taken, is `docs/DECISIONS.md` D-015. ([#14](https://github.com/skyoo2003/weft/issues/14))
- `Index.Commit` takes a `context.Context` first: `Commit(ctx, dir)`. Every caller has to be edited, which is the whole reason this is filed here rather than under Changed. It is a change and not an addition — no `CommitContext` twin exists — because `v0.1.0` is not cut, so there is no compatibility to keep, and `Search` already takes a context first. Cancelling before the manifest rename reports `ctx.Err()` and publishes nothing, leaving the pending documents pending and at most an unnamed `seg-<gen+1>` that `Open` already ignores and the next `Commit` already sweeps; cancelling after the rename is ignored, because the commit has succeeded and stopping there would leave the directory publishing a generation the live index has no mapping for. `Merge` is still uncancellable. docs/DECISIONS.md D-017 carries the argument and the two rejected alternatives. ([#16](https://github.com/skyoo2003/weft/issues/16))
- Three lines: `Index.Delete(string) bool`, `Index.Update(Document) (DocID, error)` and `ErrNoSuchKey`. `Delete` returns a bool because the only way it fails is that the key was not there, which is the shape `Resolve` already has. `Update` returns the `DocID` the document now holds — the same one when it had not been committed yet, a fresh one when it had — and refuses a key no live document holds rather than inserting, which is `ErrDuplicateKey`'s rule read from the other side. `Len` now means one past the highest assigned `DocID` rather than the document count: the two differ once anything is deleted, and `Stats` is the live population. No existing signature changed and `public_api.txt` is untouched. ([#17](https://github.com/skyoo2003/weft/issues/17))
- `engine.New` and `engine.Open` take `...Option`, and four names are added — `Option`, `Tokenizer`, `WithTokenizer`, `Index.Tokenize` — plus the sentinel `ErrTokenizerMismatch`. **Nothing already written stops compiling:** a variadic parameter is source-compatible, and all 77 `New`/`Open` call sites in this module were left as they were. Seven lines of `pkg/engine/testdata/engine_api.txt` moved, against a five-to-seven budget written down before the code (docs/FINDINGS.md milestone 13 §1.1 and §2); `public_api.txt` did not move, because nothing outside `pkg/engine` gained a name. `Scorer`, `Fuser`, `Candidate`, `Document` and `Query` are byte-identical, and `pkg/fusion` and the graph, recency and vector scorers have a zero diff. **One thing to act on:** `Open` can now fail where it used to succeed. It returns `ErrTokenizerMismatch` when the directory's documents were split by a tokenizer other than the one passed, which is traded against every query answering zero hits for the life of the index. Pass the same `WithTokenizer` the commit was made with — or none, if the commit used none, which is every directory weft has written until now. The on-disk format is **v4, unchanged**: the check recomputes one live document's token count and compares it against the number `docoff` already stores, so v3 and v4 directories still open with nothing converted. ([#19](https://github.com/skyoo2003/weft/issues/19))
- `engine.Index.Neighbors(id) ([]DocID, bool)` is added — the DocIDs a document's `Links` point at, dangling and deleted keys dropped, resolved under one read lock. It is `Links` plus `Resolve` because doing those separately costs a traversal both halves of what it spends: `Doc` materialises the key, the text and the vector to reach a field that is none of them, and `Resolve` takes the index-wide read lock once per link. The bool distinguishes a **leaf** (true, empty) from a **missing or deleted document** (false), which a traversal needs and `Vector`'s convention would have hidden. A Key repeated in `Links` yields its DocID twice, in `Links` order: this does not deduplicate. One line of `pkg/engine/testdata/engine_api.txt`; `public_api.txt` gains the `scorer/graph` additions — `Adjacency`, `NewAdjacency`, `PPR`, `NewPPR`, `Option`, `WithRestart`, `WithPrecision`, `DefaultRestart`, `DefaultPrecision`. **Nothing already written stops compiling.** `graph.Scorer`, `New`, `NewIncludingSeeds`, `MaxDepth` and `SeedN` are unchanged, so milestone 4's published table is still re-derivable from the same names. The on-disk format is **v4, unchanged**: `Neighbors` reads the `docs` records already there and steps over the vector by arithmetic rather than decoding it, which is where the saving is — 69% of the evaluation corpus's `docs` section is vector bytes a traversal never reads. ([#21](https://github.com/skyoo2003/weft/issues/21))
- `engine.Index.Terms(prefix, limit) []string` is added — the indexed terms starting with a prefix, ascending, at most `limit` of them. It is the read a term *pattern* needs and `Lookup` cannot serve: a prefix, wildcard or edit-distance query has to know which terms exist before it can look any of them up, and nothing else said. **Sorted and then truncated, not truncated as it goes**, so which terms a limit cuts does not depend on map iteration order — the alternative answers differently on consecutive calls against an unchanged index, which is a wrong answer wearing the face of a flaky test. A limit of zero or less returns nothing, the convention every `Candidates` already uses for a non-positive k. Terms from the committed segments and from the pending segment are merged and deduplicated. `public_api.txt` gains a `# ../query` block for the new package; one line of `engine_api.txt`. **Nothing already written stops compiling**, and the on-disk format is **v4, unchanged** — this reads the term dictionary each segment already decodes at `Open`. ([#22](https://github.com/skyoo2003/weft/issues/22))
- `engine.Index.PostingBound(term) int` is added — an upper bound on how many postings `Lookup` would return, read **without decoding any of them**. A term's postings entry begins with its block count and every block but the last holds exactly the block size, so this is one varint per segment and the answer is tight to within one block per segment. It exists so a caller can size a per-query accumulator before it starts filling one; `scorer/text` is the first caller and the Fixed entry beside this carries what it was worth. **A bound, not a count**, and both halves of that matter: a bound below the truth is a map that grows anyway, while a caller treating it as a document frequency would be reading a number that does **not** subtract tombstones — a deleted document keeps its posting and `Lookup` filters at read time. Zero means no segment claims the term and nothing is pending for it. Nothing else about the value is promised. One line of `pkg/engine/testdata/engine_api.txt`; `public_api.txt` does not move. **Nothing already written stops compiling**, and the on-disk format is **v4, unchanged** — the block count this reads has been written since version 1, and `decodeTermPostings` already computed the same bound internally to size `Lookup`'s slice. ([#23](https://github.com/skyoo2003/weft/issues/23))
- **`engine.Document` gains a sixth field, so an unkeyed composite literal stops compiling.** `engine.Document{"k", "text", nil, nil, t}` must become a keyed literal; every call site in this module already used keys and none changed. That is the one break. Added: the `Field` struct, `Document.Fields []Field`, `func FieldTerm(name, token string) string`, the sentinel `ErrBadField`, and `text.NewField(ix, field) *Scorer`. `text.Scorer.Name` now answers `"text:title"` for a field-scoped scorer and is unchanged at `"text"` for the plain one, so milestone 4's published arms still name themselves the same way. Six lines of `pkg/engine/testdata/engine_api.txt`; `public_api.txt` gains `NewField` under `scorer/text`. Two things that follow and are not obvious: `DocLen` and `AvgDocLen` now count every field's tokens for a document that has any, because field terms are ordinary postings and `Scrub` checks a document's frequencies against its stored length — so adding a field to an existing corpus changes BM25 scores for those documents. And `Open` reports `ErrTokenizerMismatch` against the full token count, fields included, so the guard keeps meaning what it says. ([#24](https://github.com/skyoo2003/weft/issues/24))
- **`query.Glob` takes a field as its second argument**, so `query.Glob(ix, "go*")` becomes `query.Glob(ix, "", "go*")` for Document.Text or `query.Glob(ix, "title", "go*")` for a field. That is the one break, and it is taken rather than wrapped: the alternative was a caller spelling `engine.FieldTerm("title", "go") + "*"`, which reads badly and leaks the separator into every call site. Added: `Range`, `Fuzzy`, `EncodeInt`, `EncodeTime`, and the constant `MaxEditDistance`. `Glob`, `Range` and `Fuzzy` now share one scoring implementation with three selection rules, so a stream names its field — `"glob:title"`, `"range:price"`, `"fuzzy:author"` — the same convention `scorer/text` uses. `public_api.txt` moves; `engine_api.txt` does not, and the on-disk format is **v5, unchanged** — all of this reads the term dictionary each segment already decodes at `Open`. ([#25](https://github.com/skyoo2003/weft/issues/25))
- `query.Parse(ix, string) (Plan, error)`, the `Plan` struct with its `Scorers []engine.Scorer` field, and `Plan.Fuse(engine.Fuser) engine.Fuser` are added. `public_api.txt` gains them; `engine_api.txt` does not move and the on-disk format is **v5, unchanged** — the parser composes the scorers that already existed and adds no index structure. **Nothing already written stops compiling.** `Plan.Scorers` is exported and the constraint indexes are not: a caller may inspect, reorder or extend the scorer list, and the constraints are positions into it that only `Fuse` can apply — reordering `Scorers` after parsing therefore invalidates them, which is why `Fuse` is a method rather than a free function taking a list. ([#26](https://github.com/skyoo2003/weft/issues/26))
- Two names are added for scorers that stream rather than accumulate. `engine.BlockCursor`, from `Index.BlockCursor(term)`, walks one term's postings a block at a time with `Next(buf)` and `Err()` — Scanner-shaped, because `Next` returning nil cannot carry the difference between "the term ended" and "the term could not be read", and a short posting list is not a smaller answer but a wrong one. It is **not a snapshot**: extents are read once and bytes per block under a fresh lock, so a merge landing mid-walk is reported through `Err` rather than silently truncating, and it holds no pointer into a mapping between calls, which is what makes it safe at all. `engine.Collector`, from `NewCollector(k)`, keeps the best k out of a stream in memory bounded by k — `TopK` is the same selection with the stream already in a slice, and a slice that is never built cannot be sized to the corpus. **`Index.PostingBound` is replaced by `Index.PostingCount`**, which is exact and subtracts tombstones where the bound did neither. That is a correction and not a rename: the bound was added to size an accumulator, document-at-a-time has no accumulator, and the number a cursor *does* need is the collection frequency BM25 divides by — an IDF computed from a bound drifts every score in the corpus by an amount depending on where the block boundaries fell. It costs one counting pass per term, with postings decoded and never collected. Format **v5, unchanged**. ([#29](https://github.com/skyoo2003/weft/issues/29))

### On-disk format

- Version 1, described in docs/FORMAT.md. Nothing to migrate from — this is the first tag. ([#9](https://github.com/skyoo2003/weft/issues/9))
- Version 2. Version 1 indexes are refused with ErrBadVersion and are not migrated — weft has no users and the only v1 directory in existence is rebuildable, which is an argument available exactly once (docs/DECISIONS.md D-007). New sections docoff and keys let a DocID or a Key reach its document without decoding the documents in front of it; per-unit checksums let one record, block or entry be verified without reading the whole file; the manifest's segment entries now carry (name, base, count). ([#9](https://github.com/skyoo2003/weft/issues/9))
- Version 3. One new section, ivf, holding an IVF-flat partition of a segment's vectors: spherical k-means centroids and the segment-local DocIDs assigned to each, each inverted list sealed with a CRC-32C seeded with its own list number. Version 2 indexes are read without conversion — a v2 segment reports no partition and answers with every id it holds, which is the same fallback a pending segment and a segment below 16,384 documents already need, so it costs a branch that had to exist anyway. Index.Merge upgrades a v2 generation to v3 as a side effect of the maintenance an index already performs. Version 1 is still refused. This discharges the obligation FORMAT.md section 7.6 placed on a version 3 (docs/DECISIONS.md D-008). ([#11](https://github.com/skyoo2003/weft/issues/11))
- Version 4. One new file, `dead-<gen>`, holding the whole tombstone set of the index as ascending DocID deltas, plus one uvarint on `MANIFEST` counting them and one on `meta` recording how many of a segment's documents were live when it was written. The file sits beside `MANIFEST` rather than inside a generation because a commit that only deletes documents publishes no segment; `Commit` and `Merge` both republish it under their own generation and `prune` keeps exactly the live one. Version 3 and version 2 directories are read without conversion — no tombstone file means nothing was deleted, and a `meta` with no live count means every document it held was live — so a v3 segment beside a v4 one is the ordinary state of a directory committed to since the upgrade. The version bump is the point rather than the price: nothing names the new file, so a build that predates it would answer with every deleted document still sitting in the segments, and a v4 `MANIFEST` makes such a build refuse the whole directory at the first frame it parses. Version 1 is still refused. ([#17](https://github.com/skyoo2003/weft/issues/17))
- **Version 5.** Each `docs` record gains a field block — `field count uvarint`, then `name string` and `text string` per field — appended after the timestamp and before the record's own checksum. No section is added, none moves, and `segSectionsFor` hands v3, v4 and v5 the same seven, so **v2 through v5 are all read** and a v4 record is a v5 record with the count absent. Version 1 stays refused. The bump is the point rather than the price: a field's tokens are ordinary postings that count toward the document's stored length, so a build predating fields would read a v5 segment, find frequencies it cannot account for against that length, and refuse it as **corrupt** — damage reported for a segment that is intact. Stamping the frame with 5 makes it refuse at the version check instead. `docs/FORMAT.md` §7.9 records what this cost and the rule it leaves behind: version 5 appended to a **record**, which is a checksummed unit inside a section whose offsets live in a second file, so one appended field moved every record's checksum, every `docoff` entry behind it and both frame checksums. Appending a *section* would have left the record untouched. **Append to a section, not to a record, unless the field belongs to the record's identity.** ([#24](https://github.com/skyoo2003/weft/issues/24))

- 1.26. This is the floor, not a tested ceiling — newer is untested rather than unsupported, and the gate pins this one line rather than a matrix. ([#9](https://github.com/skyoo2003/weft/issues/9))

### Added

- `weft-eval recall` and `make recall` measure what nDCG cannot see about an approximate vector index: overlap with a brute-force scan, candidates scored per query, latency both ways, and the working set a query actually reaches in bytes and in distinct pages. A partition that loses half the true neighbours holds nDCG steady when the neighbours it lost were unjudged, which on 50 queries against 171,332 documents is most of them. ([#11](https://github.com/skyoo2003/weft/issues/11))
- `weft-eval bench` and `make bench` publish a latency distribution rather than a mean: an open-loop arrival ladder at 12.5%, 25%, 50%, 100% and 200% of measured sequential throughput, with each request timed from its intended send time so a stall lands on every request it delayed. Every rung reports p50/p95/p99/p99.9 as measured and with the stop-the-world time charged to each sample removed, alongside GC cycles, GC CPU share, page faults and context switches. A quantile without 100 samples beyond it is left out rather than printed, and which rung the headline is quoted at is fixed by a rule registered before the numbers existed. docs/PERF.md is the measurement design. ([#12](https://github.com/skyoo2003/weft/issues/12))
- docs/PERF.md publishes the first latency distribution this project has had. weft's p99 on the 171,332-document evaluation corpus is 98.041ms at the registered load point, of which stop-the-world accounts for 279us — 0.28%. bleve v2.6.0 on the same machine, corpus, query set, arm and load generator is 47.123ms, so weft is 2.08x it against the order-of-magnitude bar the PRD set. The comparison lives in bench/, a separate module, so `go list -m all` still prints one line. Two predictions were wrong: the tail is neither the collector nor the 210MiB working set, and what it actually is turns out to be a property of open-loop measurement that bleve shares. ([#12](https://github.com/skyoo2003/weft/issues/12))
- `weft-eval bench -writes` prices what a commit costs the reads running against it, which is the question docs/FINDINGS.md milestone 3b left open. It copies the index first — a commit against the published evaluation corpus would rewrite the thing every measured number names — then drops one commit into a read load and splits the latencies by whether a request was due while the write lock was held. On the evaluation corpus a commit adding 20,000 documents holds the lock 11.641s and the worst read caught in it waits 13.142s. A commit below the partition floor skips the training entirely and costs 36ms, so the cost scales with the size of the commit rather than the size of the index. ([#12](https://github.com/skyoo2003/weft/issues/12))
- `weft-eval bench -rates 3.21,6.42,12.84,25.67` runs the rates you name, in order, instead of the sweep `-rate 0` derives from that run's sequential throughput. It exists because a derived sweep cannot ask whether a rung's result depends on the rungs before it: two runs land on different rates, so the history is confounded with the load. A named ladder gets no saturation point and no headline — it satisfies every shape check the load-point rule makes, and an operator who chose the rungs has chosen the load point at one remove, so provenance now travels with the rates rather than being inferred from their shape. Every entry is held to the bounds a lone `-rate` gets, at flag time rather than at dispatch, because a four-rung sweep whose third entry was a typo is ninety minutes spent before anything says so. The experiment it was built for is registered in `docs/PERF.md` section 5.2. No exported API under `pkg/` moved. ([#14](https://github.com/skyoo2003/weft/issues/14))
- `weft-eval bench` prints what one query allocated on each rung — KiB and allocation count per query, beside the rung total. It is the attribution `peakrss` cannot give: `ru_maxrss` is a high-water mark the kernel never lowers, so a rung can only say how much it raised the process mark, and `docs/FINDINGS.md` milestone 8 section 9 is what that costs — a memory figure explained by a mechanism belonging to an arm that was never measured. An allocation total divided by the samples that did the work is a property of the work rather than of how long the rung ran, so a claim about a fix can be held against it. Shed requests are not in the denominator, because the driver sheds by never dispatching. Both reads sit outside the measured window and the second is last in the after-snapshot block, since `runtime.ReadMemStats` is the only read there that stops the world and would otherwise charge the cycle, pause and fault counters with the instrument's own stop. A rung with no samples omits the line rather than dividing by zero or printing a zero that reads as a measurement. No exported API under `pkg/` moved. ([#15](https://github.com/skyoo2003/weft/issues/15))
- `Index.LookupInto(term, buf)` is `Lookup` writing into a buffer you own, so a caller walking several terms holds the longest posting list instead of the sum of them. That sum was 53.2% of what a query allocated on the evaluation corpus — a term's whole posting list, per term, per query — and `pkg/scorer/text` now reuses one buffer across a query's terms: 10,869.0 KiB per query against 15,691.3, with nDCG@10 identical to four decimals. The answer does not change: the same postings in the same ascending order, committed segments before pending, and the same absence when a segment claims a term it cannot decode. That last one is why this is a buffer and not an iterator — the verdict arrives after some postings are decoded, and postings held in a buffer can be discarded where yielded ones cannot, a partial posting list being a wrong answer rather than a short one. The read lock spans the same walk `Lookup`'s does and nothing of the caller's runs inside it, so scoring may still ask for a document length per posting. The result is yours to modify, which `Lookup`'s is not, and it is yours only until the next call with the same buffer. `pkg/fusion` is untouched and `go list -m all` is still one line. ([#15](https://github.com/skyoo2003/weft/issues/15))
- `Index.Delete(key)` removes an indexed document and `Index.Update(doc)` replaces one, so a corpus that changes no longer means a full re-index. A deleted document is invisible to all four scorers and to every read method — `Doc`, `Vector`, `DocLen`, `Resolve`, `Lookup`, `LookupInto`, `Nearest` — because the tombstone check lives inside `engine`'s read path rather than in any scorer: no scorer in the tree mentions deletion and `pkg/fusion` is unchanged. `Update` keeps a pending document's `DocID` and spends a new one for a committed document, since a segment cannot be rewritten. `Stats` and `AvgDocLen` drop tombstones immediately so BM25 normalizes against the live corpus; `Len` deliberately does not, because it is the id bound a corpus-walking scorer needs (docs/DECISIONS.md D-018). Nothing is reclaimed: a deleted document keeps its bytes and every `Merge` copies them forward, because renumbering would move rankings (D-019). ([#17](https://github.com/skyoo2003/weft/issues/17))
- `engine.WithTokenizer(tok)` replaces the tokenizer an index uses, and it replaces it at index time and query time together — `Add`, `Update`, `Update`'s re-tokenization of a replaced document's old text, and `scorer/text` all reach it through the new `Index.Tokenize`, so there is one function value per index and no way to configure the two sides apart. Pass it to `New` or to `Open`; both now take `...Option`, and every existing `New()` and `Open(dir)` keeps compiling and keeps meaning what it meant. What it buys a caller whose language the default splits wrongly: a Korean query for `검색엔진` finds nothing in a corpus holding `검색엔진을`, because the default cuts only at non-letters, and a ten-line character-bigram tokenizer fixes it — `ExampleWithTokenizer` is that program. weft ships no second tokenizer and no morphological analysis. The tokenizer is bound at construction and there is deliberately no `SetTokenizer`: calling one after the first `Add` would leave half a corpus in a different term space and report nothing (docs/DECISIONS.md D-022). `engine.Tokenize` is unchanged and is still the default. ([#19](https://github.com/skyoo2003/weft/issues/19))
- **The citation graph is now an index rather than a walk over documents.** `graph.NewAdjacency(ctx, ix)` reads every document's links once and resolves them into `DocID` space, forward *and* reverse, so a hop is a slice bound instead of a record decode and a locked key lookup. `Adjacency.Out`, `In` and `Degree` are the graph query surface — `In` is the direction a citation corpus does not store and a query usually wants, since `Document.Links` says what a paper cites and "what cites this paper" is the reverse of every edge in the corpus. It is a **snapshot**: rebuild after ingest, which is the rule any corpus-sized side store already follows. `graph.NewPPR(adj, seed)` ranks on it by personalized PageRank — Andersen–Chung–Lang forward push, so total edge work is bounded by `1/(restart × precision)` however large the corpus is, tunable with `WithRestart` and `WithPrecision`. It exists because milestone 4 diagnosed *why* hop distance contributed nothing: with `MaxDepth 3` a candidate holds one of a handful of scores and `TopK` settles the tie group on `DocID`, which is corpus insertion order. A walk has no such ceiling. On 20,000 committed documents with 128-wide vectors and 120,000 edges the graph arm goes from **1.379 ms and 48,522 allocations a query to 236 µs and 230** — 5.8× the speed and 211× fewer allocations — against a one-off adjacency build of 93.6 ms. Whether it improves nDCG is **not claimed**: the arms are registered in `weft-eval run` and the corpus that would answer it has not been run. ([#21](https://github.com/skyoo2003/weft/issues/21))
- **`pkg/query` — the constraints rank fusion does not express on its own.** Rank fusion is a union of votes, so a scorer returning only the documents that satisfy a condition expresses a *preference* and not a filter: everything it refused comes back on another scorer's vote, with no error. `docs/ADOPTION.md` section 8 is a trial subject losing time to exactly that. `query.Must(fuse, streams...)` and `query.MustNot(fuse, streams...)` are the fix, and they compose: `query.Must(query.MustNot(fusion.Fuse, 2), 1)` is "matches, and is not a draft". Stream indexes are positions in the argument list you already fixed, the same convention `fusion.FuseWeighted` uses — so nothing here learns what a scorer is, and `go list -deps ./pkg/query` names none. **A stream index past the end of the list drops everything**, because a constraint that cannot be evaluated is not satisfied and that is the wrong answer that gets noticed. `query.Glob(ix, pattern)` is the term-pattern query — `go*` prefix, `*ing` suffix, `organi[sz]e` alternation, `gop?er` single character — matched with `path.Match` against indexed terms, so a malformed pattern is an error rather than a query that quietly returns nothing. It scores TF-IDF, deliberately not BM25: under rank fusion a pattern query owes a non-degenerate ordering, not a calibrated score. `query.Phrase(ix, inner, phrase)` keeps only the candidates whose text holds the phrase as consecutive tokens, decided from `Document.Text` because a `Posting` carries a frequency and not a position — cost bounded by what `inner` nominates rather than by the corpus. Surviving candidates keep `inner`'s scores, so wrapping the text scorer still ranks by BM25. **Both scorers return every match rather than truncating to k**, which is what makes them usable as restrictions. Not here: fuzzy matching, field restriction, numeric ranges and a string query syntax. ([#22](https://github.com/skyoo2003/weft/issues/22))
- **`weftd` now speaks most of the OpenSearch query DSL, and refuses the rest by name.** `match` (both operators, with `fuzziness`), `match_phrase`, `term`, `terms`, `prefix`, `wildcard`, `fuzzy`, `range`, `exists`, `bool` with `must`/`must_not`/`should`/`filter`, and `from`/`size` paging — each mapped onto `pkg/query` with **zero lines under `pkg/`**. Field mappings arrive with them and exist for one reason: `query.EncodeInt` only works when the same encoding is applied at index time and at query time, and over HTTP those are two different processes. Five types — `text`, `keyword`, `date`, `integer`/`long`, `knn_vector` — kept in `<index>/_mapping.json` beside the `_source` store and published by the same atomic rename; any other type is refused rather than silently demoted to `text`, because a range over a demoted field matches nothing with nothing to report. `_bulk` speaks NDJSON through one hold of the index writer, reports per item, and refuses a batch whose action and source lines are off by one — that shape would write documents under each other's ids with a 200 on it. Two fuzz targets join `make fuzz`: `FuzzParseDSL` (which executes the plan, not only parses it) and `FuzzParseBulk`, at 5.8M and 3.6M executions with no crash. **The refusal rate is counted rather than claimed: 8 of 25 documented rows, 32.0%** — under the 50% at which "OpenSearch compatible" would have had to become "OpenSearch wire subset" — and `TestTheRefusalRateIsCounted` fails in both directions, so a row that quietly changes behaviour breaks the build instead of the documentation. ([#25](https://github.com/skyoo2003/weft/issues/25))
- **Hybrid search over HTTP, and the fourth signal that measures what the wire charges for one.** `knn` becomes a `scorer/vector` stream, `hybrid` fuses any number of sub-queries through `fusion.Fuse`, and an optional `weights` array — weft's, not OpenSearch's, which puts the weighting in a search pipeline — becomes `fusion.FuseWeighted`. A weight attaches to a **position** and never to a name, so `go list -deps ./pkg/fusion` still names no scorer package: that is D-005's repayment reaching the wire, where a client can now turn down a stream with nothing to say without the fusion learning what the stream holds. `search_pipeline` is refused with a 400 that states the thesis — normalizing two streams onto a common scale is the step this server does not have, because rank fusion reads position and never score. `function_score` with a `gauss`, `exp` or `linear` decay becomes a `scorer/recency` stream, on the date field a mapping marks with `"recency": true`; the decay's *parameters* are refused, because `scorer/recency` has a fixed half-life and reading `scale` to ignore it would rank by a curve nobody asked for. **What the round bought is a number.** Adding that fourth signal changed **0 lines** of fusion code — asserted structurally, not by eye — and cost 57 lines in its query clause, inside milestone 1's hundred-line budget. Counted the way milestone 1 counted, the whole change is 127 lines and over budget, and the 27-line difference is one sentence: **the wire has no place to say "this date is the document's time."** In a Go program filling `Document.Time` is a field assignment; over HTTP the binding has to be carried by a mapping. The query half is as cheap as the architecture promised; the surcharge is the protocol. ([#26](https://github.com/skyoo2003/weft/issues/26))
- **The load ladder can now be aimed through a socket, and it reports the server's memory rather than its own.** `weft-eval bench -http 127.0.0.1:9200` drives a running `weftd` with the same open loop, the same rung structure, the same saturation rule and the same suspension tolerance the in-process ladder has used since milestone 5, so the difference between the two runs is the HTTP surface and the second process and nothing else. `make bench-http` starts the server, waits for it to listen, runs the ladder and stops it. **The part that decides whether such a run means anything is where the numbers come from.** A load generator can only read its own counters, and over HTTP that process holds the in-flight requests and no index at all — printing its resident set in the RSS column would be a number that is precise, stable, reproducible and about the wrong program. So `weftd` answers `GET /_nodes/stats` with its own peak RSS, page faults, GC cycles, pause total, GC CPU share and allocation counters, read from the same instruments `internal/loadgen` reads in-process, and the ladder reads them between rungs. If that read fails the run **ends** rather than falling back to the local counters, because the fallback would be wrong in exactly the way nobody checks for. The HTTP arm also does not open the local index — mapping 626 MiB into a process that never searches it would cost that mapping before a typo in the address was even reported — and `-writes` with `-http` is refused, since the write-lock probe commits into its own copy and would time a commit the measured reads never contend with. **No judgment is published yet**: the run needs the same quiet three-hour window every ladder needs, and this is the harness, not the measurement. ([#27](https://github.com/skyoo2003/weft/issues/27))
- **A query string syntax.** `query.Parse(ix, "+title:covid -draft \"airborne transmission\"")` returns a `Plan` — the scorers to run and the constraints between them — and the caller assembles it: `engine.Search(ctx, q, k, p.Fuse(fusion.Fuse), p.Scorers...)`. Two halves rather than one scorer, because a constraint in this package is a `Fuser`, and `Search` takes the fuser as a parameter precisely so the caller owns the fusion policy. `Plan.Fuse` wraps *any* base, so a parsed query can be fused with `Fuse`, with `FuseWeighted`, or with anything else — Parse decides which documents are eligible and never how the eligible ones are ranked. The syntax, whole: a bare term, `field:term`, `+required`, `-excluded`, `"exact phrase"`, `term*` (Glob), `term~` and `term~2` (Fuzzy), `field:[lo TO hi]` with `*` for an unbounded side (Range). **There is no boolean algebra** — no parentheses, no OR, no nesting — because a clause list with `+` and `-` is exactly what rank fusion can express: a union of votes with an intersection and a difference applied to it. `a OR (b AND c)` would mean a query tree and an evaluator over it, which is a different engine and not a parser. What the flat list buys is that every query is a set of streams the caller can see, weight and reason about. An unterminated quote, a malformed or inverted range, a phrase with no terms, and an out-of-range edit distance are all **errors** rather than queries that quietly return nothing. An empty query is a plan with no scorers, so a caller taking input from a text box needs no branch for the empty case. ([#26](https://github.com/skyoo2003/weft/issues/26))
- **`make bench-head` — a head-to-head against bleve that runs in under a minute.** The existing `make bench` drives an open-loop load ladder against a prepared TREC-COVID index: it needs a corpus that is not in the repository, it takes about 90 minutes, and it has come back void three rounds running. This asks the smaller question that one cannot be waited on for — for one query, sequentially, how much work does each engine do — on a corpus it generates. It lives in the `bench` module beside the ladder, so weft's zero-dependency claim is untouched. **It is not a tail, not a throughput figure, and not a quality comparison**: bleve stems and removes stopwords where weft's default tokenizer does neither, so the two are not searching the same term space and no nDCG figure may be derived from it. What it is for: a change to the query path can now be checked against an engine that is not weft, before the ladder is available to confirm it. ([#28](https://github.com/skyoo2003/weft/issues/28))
- `weft` is a command with subcommands — `index`, `search`, `inspect`, `check` and `encode` — and between them they reach every callable symbol the library exports but three. `search` takes weft's own query string with `-q`, builds streams with `-scorers` (text, text:FIELD, vector, graph, graph:seeds, graph:ppr, recency), discounts them by position with `-weights`, and prints each scorer's own rank beside the fused one with `-breakdown`. `inspect` reads the index's own bookkeeping: stats with Len beside Stats so tombstones are visible, one document, a term's postings, the term space, the nearest vectors, the whole link graph, and `-analyze`, which needs no index at all. `check` is `engine.Scrub`, which nothing in this repository had ever called. `encode` prints the order-preserving term an integer or a time is indexed under, without which a numeric range query cannot be written by hand. ([#26](https://github.com/skyoo2003/weft/issues/26))
- weftd carries the graph signal, both halves of it. A mapping binds a keyword field with `"links": true` — the wire cannot tell one array of strings from an array of document ids, so the mapping says which — and the `weft_graph` clause walks from `seeds`, with `include_seeds`, `ppr`, `restart` and `precision` reaching the rest of `pkg/scorer/graph`. Nine more routes reach the half of engine a search request never touches: `_flush`, `_refresh`, `_forcemerge`, `_count` and `_analyze` under OpenSearch's own names, and `/_weft/terms`, `/_weft/postings`, `/_weft/scrub` and `/_weft/query` under a prefix OpenSearch does not use. `pkg/` changed 0 lines. ([#26](https://github.com/skyoo2003/weft/issues/26))

### Changed

- Open maps segments instead of decoding them, so opening an index costs the vocabulary rather than the corpus — 54 ms against 979 ms on a 171,332-document index. Commit writes only what was added since the last one; on a 7.2 MB corpus a commit after one Add writes 245 bytes, and previous generations are left untouched. Whole-file verification moved from Open into Scrub: damage inside a unit is still refused when that unit is read, and damage in bytes no decoder reaches now needs Scrub to find. ([#9](https://github.com/skyoo2003/weft/issues/9))
- scorer/vector no longer scans the whole corpus. Its loop now reads engine.Index.Nearest, which on the evaluation corpus scores 30,549 documents of 171,332 per query and returns a query 4.6 times faster. The consequence a caller has to know about is that vector results are now approximate: recall@10 against an exact scan is 0.992 and nDCG@10 for the text+vector arm moved 0.6233 to 0.6211. Nothing about the scorer's contract changed — zero norms, non-finite queries, ErrDimMismatch and context polling all behave exactly as before, and all twelve of its existing tests pass unmodified. A segment with no partition is still scored exactly. ([#11](https://github.com/skyoo2003/weft/issues/11))
- `cmd/weft` fuses the graph stream at a tenth of a vote instead of a full one, so the demo now agrees with the advice the rest of the project gives about that scorer: milestone 4 measured it contributing +0.0000 at its best weight and −0.1227 at equal weight, and both the README limitations table and the scorer's own package documentation say to weight it down. Rankings printed by the demo change. No exported API under `pkg/` moved — both golden files are byte-identical, and the weights index by stream position, so fusion still does not learn what a graph scorer is. ([#13](https://github.com/skyoo2003/weft/issues/13))
- `weft-eval bench` and the bleve comparison refuse to publish figures they did not measure. A rung reports how much wall time the process did not run for — the monotonic clock does not advance while a machine sleeps, so a ladder measured across thirteen hours of clamshell sleep previously reported every rung finishing exactly on schedule, with no shed and a headline 0.8% from the published one. Past a five-second tolerance the rung prints SUSPENDED and the summary refuses the run. A ladder cut short no longer prints a saturation point or a headline either: both commands now pass the ladder they intended rather than the rungs they reached, so an interrupted sweep is no longer indistinguishable from a complete shorter one. Rungs also print progress every thirty seconds, from a goroutine that serves no request. No exported API under `pkg/` moved — `git diff --stat pkg/` is empty for the whole milestone. ([#14](https://github.com/skyoo2003/weft/issues/14))
- Every rung of `weft-eval bench` now says how much *it* raised the process's peak resident set, or that it raised nothing and the figure beside it therefore belongs to an earlier rung. `ru_maxrss` is a high-water mark the kernel never lowers and offers no way to reset, so a rung on a ladder has always printed the peak the whole process had reached by the end of it — labelled `(process)`, and read anyway as that rung's. A pass line of the form "RSS under N at this rate" was judged against 345.2 MiB that had been reached two rungs earlier at half the rate before anything said so. The increase is the one per-rung memory statement the syscall supports; what it still cannot give is a rung's own peak once an earlier rung has set a higher mark, and `docs/PERF.md` section 2.7 says so rather than leaving it to be assumed. No published figure moves. No exported API under `pkg/` moved. ([#14](https://github.com/skyoo2003/weft/issues/14))
- `weft` with no arguments prints the help instead of starting an interactive demo over a corpus compiled into the binary. That demo is three examples now, one case each: `examples/breakdown` prints what fusion did, `examples/weights` runs one query under `Fuse` and `FuseWeighted` side by side, and `examples/sparse` is about the documents a scorer cannot see. ([#26](https://github.com/skyoo2003/weft/issues/26))

### Fixed

- Five defects in the milestone 5 load instrument, all found by review and all biased toward a flattering number. GCPause was charged over a shorter window than the latency it is subtracted from, so 64% of the p99 elapsed before accounting began; -writes stamped its commit window after the Add loop, filing the writer's own lock contention under the baseline it is compared against; the unloaded median was 50 samples where the package's own rule wants 200, and it is the denominator of every arrival rate; GCPauseTotal allocated per call, producing ~150 MiB of garbage per ladder that the report charged to the query; and GC CPU share was a ratio of process-since-start totals rather than of per-rung differences. Every published figure was re-measured afterwards — the headline p99 moved 98.041ms to 108.193ms and the collector's share of it 0.28% to 0.38%. ([#12](https://github.com/skyoo2003/weft/issues/12))
- A commit no longer stops reads. The worst read due inside a commit window now waits **61 ms** where it waited 13.072 s on the same measurement before — 214×, and below the 191 ms worst read outside the window, so the commit is no longer the worst part of a run. The window itself did not move: writing a 20,000-document batch still holds the writer for 11.3 s and nothing bounds that, but the long part of it is no longer exclusive. `Commit` encodes the segment under a read lock and takes the exclusive one only for the manifest swap, and a second mutex serialises `Add`, `Close`, `Merge` and `Commit` against each other — without it `sync.RWMutex`'s writer preference would let one concurrent `Add` restore the whole stall. `Add` still blocks for a whole commit, and `Merge` is unchanged and is a longer stop. Measured before and after on one machine with one procedure registered in advance: docs/PERF.md section 5.4, docs/FINDINGS.md milestone 9. ([#16](https://github.com/skyoo2003/weft/issues/16))
- `Scrub` no longer calls a re-added-then-deleted key damage. A key can only be re-added once its previous holder is dead, so within a segment every record for that key but the last is a tombstone at seal time and the keys entry — if there is one — names the last; `scrubDocs` kept the *first* of them, leaving the slot naming a record no entry points at, and the cross-check between the keys table and the documents then reported `ErrCorrupt` on a healthy index. `Add`, `Delete`, `Add`, `Commit`, `Delete`, `Commit`, `Scrub` was enough, and so was any second `Update` of a committed document. A live record still wins the slot over a tombstone, so the check that catches two live holders of one key is unchanged. Also fixed on the same read path: the running total of deleted tokens was an `int` where the collection total it is subtracted from is a `uint64`, so on a 32-bit build a corpus with more than 2^31 tokens deleted overflowed, widened to about 1.8e19, clamped the collection total to zero and turned BM25's length normalization off for every posting — no error, and every score different. ([#18](https://github.com/skyoo2003/weft/issues/18))
- **`scorer/text` allocated a corpus-sized map on every query, including queries that matched nothing.** The BM25 accumulator was sized to the document count, so a query for a term no document holds allocated **1.18 MB and 78 µs** building a map that never received an entry — a floor under every query on the corpus, scaling with the corpus rather than with what the query reached. On the 171,332-document evaluation index it is 4.73 MB a query, which at the 27 queries/s where `docs/FINDINGS.md` milestone 5 §3.2 saw sustained load collapse is 128 MB/s of garbage produced before a single document is scored — the same currency that section names as the wall. It is now sized to the widest posting list the query will actually walk, read through the new `Index.PostingBound`. Measured on 50,000 documents committed and reopened: a query matching nothing goes from 78,685 ns and 1,182,240 B to **151 ns and 16 B**; a term in three documents from 101,285 ns and 1,185,247 B to **982 ns and 7,166 B**; a term in one document in fifty from 176,454 ns and 1,216,432 B to **84,655 ns and 70,415 B**. A term held by every document is unchanged — 2,818,997 B to 2,818,797 B, and a time difference inside the run-to-run noise band. **No score or ranking changes**: map sizing does not touch a value, and `internal/eval/bm25_test.go` still matches `rank_bm25` to 4.44e-16. Sizing from the *first* term instead was tried and rejected: it removes the floor and costs 42% more memory on a multi-term query whose rarest term comes first, which is the realistic shape. ([#23](https://github.com/skyoo2003/weft/issues/23))
- **`engine.TopK` sorted every candidate to return ten of them.** It is the one selection path every scorer and the fuser share, and `scorer/text` emits one candidate per matching document — so a query for a term held by every document in a 50,000-document corpus arrived with 50,000 candidates, asked for ten, and paid a full `n·log₂n` sort for the other 49,990. A profile of that query put the sort and its comparator at the largest single share of work that was not the posting walk. It now takes a k-sized heap whose root is the **worst** of the best k so far, so each remaining candidate is rejected in one comparison: roughly 50 thousand comparisons against 780 thousand. `BenchmarkTopK` over 50,000 candidates: **k=10 goes from 3,956 µs to 168 µs (23.6×)** and k=100 to 130 µs, with zero allocations — the heap is `cands[:k]` itself. `k >= n` keeps the full sort, because there is nothing to select; that is the path `pkg/query`'s scorers take and it is unchanged. End to end in `scorer/text`, a query for a term in every document goes from **5,871 µs to 2,112 µs (2.78×)**, and one in a fiftieth of them from 85 µs to 35 µs. **The answer is identical**: the comparator is a total order, so "the best k" is a unique set and sorting it gives a unique sequence — `TestTopKSelectsExactlyWhatSortingWouldHaveChosen` checks the two paths against each other over every combination of n and k that exercises the boundary, and the nDCG and BM25 reference tests are unmoved. The `ponytail:` note that stood on this function named this exact condition as the one that would justify buying it. ([#27](https://github.com/skyoo2003/weft/issues/27))
- **`scorer/text` scored term-at-a-time and held three corpus-sized structures to do it.** Milestone 22 measured weft against bleve and found weft faster on every query shape and allocating **156× more** on the widest — 2.82 MB against 18 KB — which is the same quantity milestone 5 §3.2 named as the throughput wall, *live heap under concurrency*, measured for the first time against something other than weft's own past. The accumulator, the posting buffer and the candidate slice were all sized by the corpus rather than by the answer. It now walks **document-at-a-time** over one `engine.BlockCursor` per query term, scoring each document to completion and offering it to a k-sized `engine.Collector`: no accumulator, no candidate slice, and no posting list held whole. On 50,000 documents, a term held by every one of them goes from **2,819,333 B and 2,139,639 ns to 32,337 B and 944,509 ns** — 87× less memory and 2.3× faster — and against bleve it is now **3.1× faster at 1.8× the memory**, where it was 1.36× faster at 156×. On the shapes that are not the worst case weft now allocates **less** than bleve: 4.8× less on a term in a fiftieth of the corpus, 69× less on one no document holds. A middle version that held whole posting lists was tried and rejected — it removes the accumulator but holds the *sum* of the lists, which is worse than the old path for a query whose terms are all common, and `TestScoringDoesNotAllocateAPostingListPerTerm` is what caught it. **No score or ranking changes**: the reference tests matching `rank_bm25` to 4.44e-16 and `pytrec_eval` are unmoved. ([#29](https://github.com/skyoo2003/weft/issues/29))

### Security

- Commit now creates its index directory and segment directories with mode 0o700 rather than 0o755. The corpus is the caller's data and nothing weft does needs another user on the machine to read it — including the caller's own group, which 0o750 would let read the 0o644 segment files inside. ([#9](https://github.com/skyoo2003/weft/issues/9))
- CodeQL runs on every Go change and once a week, and SECURITY.md now names both automated gates rather than only the fuzz one. It is the half of the decoder question `make fuzz` cannot reach: fuzzing finds a crash on an input it happened to generate in thirty seconds, dataflow analysis finds where a length the file chose reaches an allocation whether or not anything generated that file. Neither is in `make all` — CodeQL builds a database before it can ask anything, which is minutes — so this is the first gate with no local half, and its findings land on the Security tab rather than in a pull request check. ([#23](https://github.com/skyoo2003/weft/issues/23))
