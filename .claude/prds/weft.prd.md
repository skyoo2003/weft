# weft

> 씨실. 날실(신호)들은 서로 닿지 않고, 씨실 하나가 전부를 가로질러 묶는다.
> 신호 무관 융합 검색 엔진 — Go, 밑바닥부터.

> **개정 이력**
> - v1 — Rust/tantivy 전제
> - v2 — Go/bleve 전제. 경쟁 조사 결과 bleve가 BM25·벡터·RRF를 이미 내장함을 확인, 가설을 "그래프 신호 융합"으로 축소
> - **v3 (현재) — 밑바닥부터 개발 전제.** 기성 검색 라이브러리를 쓰지 않는다. 이 결정이 정당화 논리 전체를 바꾼다. 아래 Problem을 다시 읽을 것.

## Problem
하이브리드 검색 엔진들은 **하나의 신호로 시작해 나머지를 나중에 덧붙였다.** 역색인 위에 벡터를 붙이고, 그 위에 융합 랭킹을 얹는다. 그 결과 융합은 언제나 **특수 케이스**다 — 두 신호를 합치는 전용 코드 경로가 있고, 세 번째 신호를 넣으려면 그 경로를 다시 뜯어야 한다. 그래프 근접도가 어느 엔진에서도 1급 랭킹 신호가 아닌 이유가 이것이다.

밑바닥부터 만들면 순서를 뒤집을 수 있다: **융합을 기본 동작으로 놓고 신호를 그 위에 꽂는다.** 텍스트·벡터·그래프가 모두 동일한 "점수 스트림" 인터페이스를 구현하면, 융합 연산자는 신호가 몇 개인지, 어떤 종류인지 알 필요가 없다. 네 번째 신호(최신성, 인기도, 개인화)를 추가하는 비용이 첫 번째와 같아진다.

**방치했을 때의 비용**: 신호를 하나 추가할 때마다 랭킹 코드를 다시 쓰게 되고, 그래서 아무도 추가하지 않는다.

## Evidence
v2의 경쟁 조사는 유효하며, **밑바닥 개발을 정당화하지 않는다.** 정직하게 양쪽을 기록한다.

**밑바닥 개발에 불리한 사실 (v2에서 확인, 취소되지 않음)**
- **bleve(Go) v2.5+ 가 BM25, ANN kNN, RRF/RSF 융합을 이미 내장한다.** 텍스트+벡터 하이브리드만 필요하다면 이 프로젝트는 불필요하다. ([bleve](https://github.com/blevesearch/bleve), [v2.6.0](https://github.com/blevesearch/bleve/tree/v2.6.0))
- **SQLite 한 파일(FTS5 + sqlite-vec + recursive CTE)로 세 모드가 이미 가능하다.** 지루하지만 단일 프로세스다. ([embedded vector DB 비교](https://shaharia.com/blog/choosing-embeddable-vector-database-go-application/))
- 즉 **"할 수 있는가"는 이미 해결된 문제다.** 남은 것은 "어떤 구조로 하는가"뿐이다.

**밑바닥 개발을 정당화하는 주장 (미검증)**
- 기존 엔진의 융합은 신호 개수에 대해 열려 있지 않다 — **Assumption. 마일스톤 1이 우리 쪽을 증명하고, bleve 쪽 한계는 코드를 읽어 확인해야 한다.**
- 그래프 근접도가 랭킹 신호로서 가치가 있다 — **Assumption. 마일스톤 4에서 반증 가능.**
- 원래의 "3스토어 동기화 지옥" 고통 — **여전히 미검증.** 사용자 인터뷰 0건.

**정직한 요약**: 이 프로젝트는 시장 공백이 아니라 **아키텍처 가설** 위에 서 있다. 가설이 틀리면 bleve를 쓰는 것이 맞다.

## Users
- **Primary**: 오픈소스 인프라 기여자 — Go 인프라 라이브러리를 쓰고 고치는 개발자. 랭킹 신호를 자기 도메인에 맞게 **추가**하고 싶은데 기존 엔진이 그걸 허용하지 않는 시점에 필요를 느낀다.
- **Secondary (v3 신규, 정직 기록)**: **개발자 본인.** 밑바닥 개발은 첫 외부 가치까지 수개월이 걸린다. 그 기간 동안 유일하게 확실한 산출물은 검색 엔진 내부 구조에 대한 이해다. 이것을 부차 목표로 명시하지 않으면 마일스톤 3 즈음에 동기가 끊긴다.
- **Not for**: 지금 당장 프로덕션 검색이 필요한 팀(bleve를 쓸 것), 관리형 SaaS를 원하는 팀, Go 외 언어에서 임베드하려는 사용자.

## Hypothesis
We believe **모든 랭킹 신호가 동일한 점수 스트림 인터페이스를 구현하고 융합 연산자가 신호의 개수·종류를 모르는 Go 검색 엔진**이 **새 신호를 추가할 때마다 랭킹 코드를 다시 쓰는 문제**를 **자기 도메인 신호를 넣고 싶은 오픈소스 인프라 기여자**에게 해결해 줄 것이라 믿는다.

We'll know we're right when **텍스트·벡터·그래프 세 신호가 융합 연산자 코드를 한 줄도 바꾸지 않고 꽂히고, 네 번째 신호도 같은 비용으로 추가되며, 그렇게 만든 그래프 신호가 실제로 검색 품질을 개선할 때** 확인된다.

**반증 조건 (명시, 2단)**
1. 마일스톤 1에서 융합 연산자가 신호 종류를 알아야만 한다면 → 아키텍처 가설 실패. 설계를 다시 하거나 접는다.
2. 마일스톤 4에서 그래프 신호가 nDCG를 개선하지 못하면 → 신호 자체가 무가치. 인터페이스는 남기고 그래프는 버린다.

## Success Metrics

## Scope
**MVP** — 텍스트·벡터·그래프 세 신호가 **동일한 점수 스트림 인터페이스**를 구현하고, 신호 개수를 모르는 하나의 융합 연산자가 이를 소비해 순위를 내는 인메모리 엔진. 표준 라이브러리만 사용.

영속화·규모·성능은 아키텍처가 옳다고 증명된 **후에** 붙인다. 순서를 바꾸면 잘못된 구조를 디스크 포맷으로 굳히게 된다.

**Out of scope**
- **분산 클러스터링·샤딩·복제** — 단일 노드에서 아키텍처를 먼저 증명
- **임베딩 생성·모델 추론** — 벡터는 외부 주입 전제
- **기성 검색 라이브러리 사용** — 이 프로젝트의 전제 자체 *(v3 신규, v2에서 반전)*
- **형태소 분석·다국어 토크나이징** — 공백 분리로 시작. 한국어·CJK는 아키텍처와 무관한 별도 문제 *(v3 신규)*
- **쿼리 언어·파서** — Go API로만 쿼리 구성. DSL은 아키텍처 증명에 기여하지 않음 *(v3 신규)*
- 관리 UI·대시보드, 기존 쿼리 언어 호환, Go 외 언어 바인딩
- 프로덕션 운영 기능(백업, 스냅샷, 롤링 업그레이드)
